Project B · SCE WG1

A community library of baseline models.

The canonical models of the field, implemented and documented across the toolkits that can solve them. Same model, multiple tools, side-by-side notation, honest commentary on tradeoffs — each implementation authored and maintained by the project that built the toolkit.

Coordinated by Matt McKay

Proposed at the CEF 2026 pre-conference, Venice, 28 June 2026 · slides and pitch

01 · Why

The plurality is real but invisible

Computational economics has more than a dozen serious open-source toolkits across MATLAB, Python and Julia, each with genuinely distinct strengths. Researchers have no neutral way to compare them, no shared library of canonical models, and no on-ramp that treats the ecosystem as a whole. New users default to whatever their advisor uses; experienced researchers stay locked into the first tool they learned.

What a shared corpus buys us

  • A community asset. The field's first cross-toolkit reference — a neutral on-ramp for new users, and a showcase for the projects that build the tools.
  • A test corpus for Project A. Project A asks each toolkit team to state formally what its model files mean. A curated set of worked models is what those statements have to account for, and what a shared semantic schema can be validated against.
  • Substrate for AI assistance. Exactly the corpus an assistant needs to answer which tool fits my problem? and translate my model from X to Y. Standards make AI useful; AI makes the library findable.
  • A proving ground for standards. As shared schemas emerge from the working group — steady states, IRFs, Jacobians — the library demonstrates them in working code rather than in prose.

02 · The library

Each participating project contributes along two tracks. The first makes the toolkits comparable; the second lets each project show what it is actually best at.

Track 1

A shared baseline model

Where several toolkits solve the same class of problem, the group coordinates them around one agreed baseline — same calibration, same reported objects — so results line up side by side and divergences are visible rather than buried.

Track 2

An author's-choice showcase

A tutorial of the project's own choosing, on the problems its toolkit was built for. A common baseline alone would flatten the differences that matter; this is where each project argues its own case.

Both are published in existing notation — the model as its toolkit states it, not translated into a house dialect — with per-model metadata, an honest note on tradeoffs and limitations, and continuous integration that runs each implementation and flags breakage.

03 · Model groups

Projects are coordinated in groups by problem class, since that is the level at which a shared baseline makes sense. Four groups are proposed as a starting point:

Incomplete-markets heterogeneous agents

Candidate baselines: Aiyagari; Krusell–Smith

HANK

Candidate baseline: a two-asset HANK model

DSGE

Candidate baseline: a small New Keynesian DSGE model

Agent-based macro

Candidate baseline: a baseline ABM macro model

Not yet fixed  The groups and their baseline models are a proposal. Which baseline a group adopts follows from what its toolkits can actually solve — see how a baseline is agreed below. Agreeing them is an early milestone, not a precondition for joining.

04 · Agreeing a baseline

Agreeing what the shared baseline is — precisely enough that results line up, without prescribing how it should be solved — is the hard part of this project. It is run as a specification process with a named author, not as a design committee.

Step 1

A capability survey at sign-up

Every project completes a short capability survey when it joins the working group — model classes it solves, treatment of aggregate risk, constraints, the objects it reports natively. The responses compose the capability matrix.

Step 2

The matrix picks the model

Within a group, what every toolkit can actually solve defines the feasible baselines. The model is chosen from that intersection and anchored on a published paper with its own calibration, so the group transcribes and disambiguates rather than designs.

Step 3

A model specification architect

Each group has one named architect who authors the specification. The group comments asynchronously; open questions are settled in the issue tracker, and the co-chairs arbitrate anything that stalls. The specification is versioned and credited to its author.

Step 4

Tutorials are submitted against it

Once frozen, the specification is what each project implements and writes its tutorial against. A specification is not frozen until two independent implementations reach the agreed tolerance — the first divergence between them is the best review the document will get.

The spec pins
  • Functional forms, timing conventions, normalizations
  • Parameter values, and where they come from
  • Target moments of the exogenous processes
  • Which objects are reported, in what units
  • The tolerance at which two results count as agreeing
The spec leaves free
  • Solution method and algorithm
  • Grids, discretization, basis functions
  • How the exogenous process is discretized
  • Language, code structure, API
  • Everything the toolkit exists to do differently

Where implementations diverge beyond tolerance, the divergence is documented and attributed to method — it is a result of the exercise, not a failure of it. A project that cannot match one element of a specification exactly contributes with a documented deviation rather than dropping out. Phase 1 publishes no timings and no ranking of toolkits.

05 · The ask

What each project provides

  • Agreement in principle to take part.
  • By end of 2026, the shared baseline model in its toolkit, coordinated with the other projects in its group so results line up side by side.
  • An author's-choice showcase tutorial highlighting where the toolkit is strongest.
  • Both authored and maintained by the project, under CC-BY for text and an OSI-approved licence for code.

What each project keeps

  • Authorship credit for its contributions.
  • Editorial control over how its tool is presented.
  • The right to update or withdraw contributions at any time.

The library curates and publishes; it does not take ownership of anyone's work, and it does not rank the toolkits.

06 · Who does what

The working group

Governance sits with WG1: the model list, the baseline specifications, coordination within each group, and editorial standards for the collection.

Participating projects

Author and maintain their own implementations and tutorials. Toolkit-specific content stays the contributors'.

QuantEcon

Partner in the organising body: hosts and publishes the collection, and builds the ecosystem glue the group identifies — open-in-local-MATLAB / Octave / Julia handlers, schema validators, CI converters between toolkit output formats.

Econ-ARK

Anchors a distinct semantic-representation track. Once the curated library exists, its models become the corpus for expressing economic models in a shared schema — documented and taught alongside the implementations, and validated against the library itself.

07 · Roadmap

Phase 1 6–12 months

Community library

  • 3–4 canonical models in 2–3 toolkits each, published on a static JupyterBook site.
  • Open-source repository, PRs welcome.
  • Per-project tutorials and per-model metadata.
  • CI runs the implementations and flags breakage.
  • An AI advisor MVP built on the corpus.
Phase 2 12–24 months

Reference standard

  • Shared output schemas and a queryable index.
  • Cross-toolkit validation reports: where do the same model's outputs diverge?
  • Library models expressed in a shared semantic representation, building on Econ-ARK's DP schema.
  • Documentation of that design, plus a how-to tutorial.
